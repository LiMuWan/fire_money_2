# UI 解耦与重构规范

本规范作为 [UI_WORLD_CLASS_TERMINAL_DESIGN_2026-04-19.md](C:/Users/18335/Documents/New%20project/docs/UI_WORLD_CLASS_TERMINAL_DESIGN_2026-04-19.md) 的工程落地补充，约束后续所有 UI 改版、页面扩展、Toggle 新增与重构行为。

目标不是“先把功能堆上去再收拾”，而是从一开始就把页面、状态、行为和代码结构做成可维护的机构终端形态。

## 1. 总原则

- UI 设计优先于代码重构；先把页面做对，再决定代码怎么拆。
- 重构不是主目标，重构只是服务于设计落地的手段。
- 如果一个改动同时可以“继续重构代码”或“继续统一 UI 设计”，默认优先继续统一 UI 设计。
- 一个 Toggle 对应一个明确职责，不承载多个无关功能。
- 一个页面只承载一条主链路，相关但非核心能力默认折叠、下沉或拆出。
- 页面负责组合，不负责堆积业务逻辑。
- 样式、文案、布局、刷新逻辑、业务判断尽量分层，不混写在同一大函数里。
- 能抽配置就不写死，能抽构建器就不堆在主窗口，能抽控制器就不留在 UI 事件里。

### 1.1 控件复用原则

从现在开始，UI 改版默认先判断“能否复用”，再判断“是否重写”。

补充：

- 这里的“复用”首先服务于视觉统一，而不是服务于减少代码行数。
- 只有当现有控件无法满足页面设计目标时，才进入重构或重写。

优先复用顺序：

1. 复用现有终端骨架组件
2. 复用现有页面结构模式
3. 复用现有状态文案 / tooltip / action 词典
4. 最后才是新增局部组件

必须优先复用的组件层：

- `workspace hero`
- `status banner`
- `focus strip / judgment strip`
- `stage summary`
- `summary cards`
- `action row`
- `terminal panel`
- `terminal table`
- `note panel`

不允许的做法：

- 为某一个页面单独再造一套状态条样式
- 为同一种辅助动作再写一套不同短标签
- 为同类页面重复拼接近似但不一致的 Hero / Banner / 判断条结构
- 为了解决局部问题，直接在页面里临时加一排新按钮或新卡片而不复用现有骨架

## 2. 页面解耦规范

### 2.1 一页一主链

每个工作区必须先定义自己的主链：

- 全局态势：市场判断链
- 接入中心：账户接入链
- 机会池：候选到计划链
- 执行中控：委托到回执链
- 信号扫描：扫描到观察链
- 涨停策略：专项候选到回封链
- 单票复盘：单票证据到结论链
- 策略配置：参数到风险边界链

如果一个页面出现两条以上同权重主链，必须拆。

### 2.1.1 视觉拆分判定规则

以后判断“一个页面在视觉上要不要拆分”，统一按下面这套规则执行。

先问 4 个问题：

- 这个页面是否同时承载两个以上不同阶段的主任务？
- 用户在完成任务时，是否需要在同一页里来回切换两种以上不同心智模式？
- 首屏是否同时出现三个以上同权重的大区块，且没有明显主次？
- 某个 Toggle / workflow 节点是否实际上在切换不同页面语义，而不是同一对象的不同观察角度？

判定规则：

- 满足 `2 条以上主任务`，必须拆页。
- 满足 `不同心智模式`，优先拆成子页面或独立工作区。
- 满足 `首屏 3 个以上同权重大区块`，优先拆成子页面，再谈样式优化。
- 满足 `Toggle 背后是不同流程阶段 / 不同对象 / 不同结果区`，必须拆成独立主视图。

什么叫“不同心智模式”：

- 判断市场 vs 执行交易
- 建立候选 vs 复核单票
- 管参数 vs 管消息源 vs 管 AI
- 跟踪模拟盘样本 vs 跟踪真实委托

什么情况不需要拆：

- 同一个对象的不同观察角度
- 同一条主链里的前后相邻动作
- 只是信息密度不同，不是任务不同
- 只是辅助证据，不是独立主任务

不拆时允许的形式：

- Tab
- 折叠区
- Drawer
- More Menu
- 指标卡切换

拆分优先级：

1. 先拆成独立工作区
2. 其次拆成页面内子页面
3. 最后才是折叠/抽屉

如果一个模块会改变“我现在在哪、我该做什么、结果去哪看”这 3 件事中的任意 2 件，就不要再把它留在同一主页面里。

### 2.2 Toggle 使用规范

Toggle 只能承担以下 3 类职责之一：

- 视图切换：同一数据对象的不同观察视角
- 信息密度切换：标准 / 紧凑 / 盯盘
- 辅助能力开关：显示或隐藏非主链辅助模块

不允许：

- 用一个 Toggle 同时切换数据源、业务模式、操作权限
- 用一个 Toggle 挂多个面板和多套不相关逻辑
- 把“是否显示”与“是否执行”混成一个开关
- 把同一个 Toggle 当成两个不同页面的入口

### 2.2.1 Toggle 与页面边界硬规则

- 一个 Toggle 最多服务一个页面语义。
- 如果 Toggle 改变的是“我现在在哪个页面 / 我在处理哪条主链 / 我该看哪类结果”中的任意两项，就必须拆页。
- Toggle 只适合切观察角度、密度或辅助层，不适合切 workflow 阶段。

### 2.3 辅助功能下沉原则

以下能力默认不占首屏主位：

- 导出
- 模板生成
- 运行维护
- 历史统计
- 解释性长文本
- 调试信息

它们应进入：

- Drawer
- 次级 Tab
- 更多菜单
- 折叠区

## 3. 代码解耦规范

### 3.1 主窗口职责边界

`QuantHunterWindow` 只保留以下职责：

- 组装工作区
- 管理全局状态引用
- 路由切换
- 调用 builder / refresh / controller

不建议继续把以下内容堆进主窗口：

- 单页构建细节
- 大段样式字符串的业务分支
- 表格逐列填充逻辑
- 各页面的按钮状态推导
- 某个页面的专属状态机

### 3.2 推荐拆分层次

后续功能优先按以下层次拆：

1. `workspace_builders.py`
   用于页面结构与组件装配
2. `ui_refresh.py`
   用于页面刷新、表格填充、状态回写
3. `ui_*_patches.py`
   用于阶段性 UI 升级和增量改版
4. `ui_controllers.py`
   用于按钮动作与业务调用桥接
5. `ui_config.py`
   用于命名、文案、表头、固定映射

### 3.3 Builder 规范

Builder 函数只做：

- 组件创建
- 布局编排
- 默认文案
- 信号连接

Builder 不做：

- 大量业务判断
- 数据计算
- 风险评估
- 提交状态推导
- 长链路条件分支

### 3.4 Refresh 规范

Refresh 函数负责：

- 把现有状态映射到界面
- 填充表格、面板、指标卡
- 控件显隐与按钮可用性更新

Refresh 不负责：

- 创建控件
- 修改路由结构
- 永久性重排布局

### 3.5 Patch 规范

Patch 文件只能做一类改造：

- 命名改版
- 终端壳层改版
- broker 页重排
- workflow bar 改版

不允许一个 patch 文件同时承担：

- 页面构建
- 状态推导
- 业务逻辑
- 表格数据源生成

### 3.6 样式规范

样式优先级：

1. 全局 token / theme
2. 页面级 objectName / property
3. 少量局部覆盖

不建议：

- 为某个按钮临时拼大段样式
- 同一组件在多个文件里重复定义视觉规则
- 通过 patch 不断叠加重复 QSS

## 4. 页面内模块拆分规范

每个工作区建议按“主链模块 + 辅助模块”拆。

示例：

- 执行中控
  - 主链模块：执行摘要、委托执行台、当前委托详情、执行回执
  - 辅助模块：账户配置、运行维护、偏差复盘

- 机会池
  - 主链模块：当前焦点、今日计划、执行队列
  - 辅助模块：题材热度、龙头榜、AI 复核、消息中心

模块拆分后，每个模块至少满足：

- 有独立标题
- 有独立状态
- 有独立刷新入口或刷新函数
- 可单独折叠或重排

### 4.1 页面首屏结构规则

所有页面默认先按下面这套结构组织首屏：

1. `Hero`
2. `状态条`
3. `判断条`
4. `摘要/指标`
5. `子页面 / 主视图区`

如果首屏不符合这套结构，后续新增功能前优先补结构，不优先继续堆模块。

例外情况只允许两种：

- 纯配置页
- 纯表单页

即便是这两类页面，也应至少保留 `Hero + 状态条 + 判断条` 的首屏骨架。

## 5. 重构触发条件

出现以下任意情况，必须优先重构再继续叠功能：

- 一个函数超过 200 行且混合布局、文案、状态、逻辑
- 一个页面首屏出现 3 个以上同权重主区块
- 一个 Toggle 控制两个以上不相关面板
- 同一文案映射在 3 个以上文件重复出现
- 同一表格列宽或对齐规则在多个地方重复写死
- 后续改一个按钮文案需要改 3 个以上文件

## 6. 新功能接入检查清单

以后每次加页面、加 Toggle、加区块，都必须先过这份清单：

- 这个功能属于哪个工作区主链？
- 如果不属于主链，为什么不下沉到折叠区或更多菜单？
- 它是否已经可以复用现有 Builder / Refresh / Controller？
- 它是否已经可以复用现有 Hero / 状态条 / 判断条 / action row / terminal table？
- 是否会让当前页面出现第二条主链？
- 是否引入新的重复文案、重复样式、重复表格规则？
- 是否需要先抽配置而不是直接写死？

## 7. 对当前项目的直接约束

从现在开始，以下事项作为默认规范：

- 不再接受“一个页面继续加很多无关功能”的改法。
- 不再接受“一个 Toggle 控多个不相关面板”的改法。
- 视觉设计优先按“主任务 / 心智模式 / workflow 阶段”判断是否拆页，而不是先看能不能塞下。
- 新页面或大区块优先拆进 `workspace_builders.py` 和 `ui_refresh.py`。
- 新增 UI patch 必须保持单一主题。
- 任何首屏新增能力，都要先说明它属于主链还是辅助层。
- 如果某页已经过重，优先做重排、折叠、下沉和拆模块，而不是继续叠组件。

## 8. 当前建议的下一步重构方向

- 把各工作区 Hero、Banner、状态语义进一步集中到统一配置。
- 把表格列优先级、列宽、对齐规则抽成统一映射。
- 把 broker / recommend / overview 的“辅助区显示策略”抽成独立配置。
- 逐步减少 `app_qt.py` 对页面级细节的直接持有。

## 9. 当前页面拆分判断

按上面的规则，对当前主要工作区先做如下判断：

- `全局态势`：暂不拆独立工作区，但保留多子页面。
原因：同属“市场判断链”，只是观察角度不同。

- `接入中心`：暂不拆。
原因：主任务仍是账户接入链，复杂度还在可控范围。

- `机会池`：需要拆子页面。
原因：候选排序、执行审查、战法工作台、复盘消息已是多心智模式。

- `执行中控`：保留主工作区，但实验必须拆出。
原因：真实委托链和模拟实验链不是同一主任务。

- `实验台`：独立工作区，但应拆子页面。
原因：模拟盘样本、主测/对照、实验结论属于独立 workflow，且在同一页会形成三块同权重主视图。

- `信号扫描`：暂不拆独立工作区，但应拆子页面。
原因：扫描、观察池、监控仍属于同一条扫描到观察链，但已形成三个同权重视图。

- `涨停策略`：暂不拆独立工作区，但应拆子页面。
原因：候选判断和回封监控属于同一专项执行链，但已经形成两个不同认知模式的主视图。

- `单票复盘`：需要拆子页面。
原因：单票总览、信号交易、历史战法是不同层级证据。

- `策略配置`：必须拆子页面。
原因：参数、战法、消息源、AI、说明是不同主任务。
